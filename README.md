# recepten

AuDHD-friendly recipes: a wheel that chooses, cook mode with parallel tracks, backward timing, bad days

Built on [chassis](https://github.com/kennypassenier/chassis-rs): the
service gets configuration, logging, `/healthz`, `/metrics`, a graceful
stop, a dashboard with per-client tokens, signed self-update and webhooks
from the kit, and adds only what it does itself (`src/main.rs`).
What the kit provides — tokens, pages, health, update, the knob table —
is in [docs/KIT.md](docs/KIT.md), generated by `chassis sync`.

## Run it

```bash
cargo run -- --help                 # every knob, three names each
recepten gen-secret               # on a terminal: the two lines the env file needs
RECEPTEN_TOKEN=… RECEPTEN_SECRET_KEY=… cargo run -- --listen 127.0.0.1:8080
```

Open http://127.0.0.1:8080, log in with the token, add a client on the
Clients page, copy its token, and call the API with
`Authorization: Bearer <token>`.

## Configuration

Precedence: flag > environment variable > `/var/lib/recepten/config.toml` >
default. `recepten --print-config` shows every effective value and where
it came from; `recepten --check` validates without opening a socket.
Secrets (`RECEPTEN_TOKEN`, `RECEPTEN_SECRET_KEY`) come from the
environment only, never from the file.

## Deploy

`deploy/recepten.service` is the systemd unit (`Type=notify`, hardened);
`deploy/service.yml` is the homelab's stack file for `homelab adopt`;
`Dockerfile` builds the container image `chassis release` pushes to GHCR.
The image runs as its own user and owns `/var/lib/recepten`; a **named
volume** inherits that owner, a **bind mount** does not — `chown` the host
directory to the container's uid first, or the first login fails with a
503 ("cannot write sessions store"). Log rotation is the runtime's job:
under systemd journald rotates (the `deploy/journald.conf` drop-in caps the
LXC's journal), under docker set `logging: options: max-size` in the
compose file.

## Staying on the kit

```bash
chassis sync            # diff the kit-owned files, check the kit tag and kp_themes
chassis sync --remote   # also compare main's branch protection with the kit's (needs gh)
chassis sync --write    # apply the kit's files and correct kp_themes
```

Exit 1 means drift: a file diff, or a `! …` line naming what differs and
how to fix it (kit tag in `Cargo.toml` vs `.chassis.toml`, `kp_themes`,
a workflow file the kit no longer ships). Without `--remote` it needs no
network, so a script can run it as a drift check.

## Release

```bash
chassis release 0.2.0
```

runs the full gate on this machine (fmt, clippy, tests, the project's own
gates, cargo-deny, the image smoke), bumps the version, commits and tags,
builds the static binary, `SHA256SUMS` and the image here, pushes main, the
tag and the image, creates the GitHub release, then signs the manifest with
your minisign key and uploads `SHA256SUMS.minisig` and `VERSION` — the four
assets the self-updater needs. `chassis release 0.2.0 --dry-run` runs the
gate and builds every asset, then stops before any commit, tag or upload.
It needs docker logged in to `ghcr.io` with a token that has
`write:packages`, `gh`, `cargo-deny` and `minisign`.

## Development

Gates are git-native. After a fresh clone:

```bash
git config core.hooksPath .githooks
```

Every commit then runs fmt, clippy (warnings are errors) and the tests,
and must carry feature IDs in brackets (`[K3]`, `[meta]`).
